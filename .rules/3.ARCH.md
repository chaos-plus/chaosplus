# Arch


## 端类型定义

> 具体端的数量与命名由各项目 PRD 定义；下面是通用的端分类模型，供各项目对号入座。

- 系统管理端（SYS）：面向平台运维/管理员，管理全局配置与租户
- 运营端（OPS）：面向平台运营人员，处理运营类事务
- 业务管理端（APP）：面向租户/业务方的管理后台
- 终端用户端（WEB）：面向最终用户的客户端（Web / 移动端）


## 架构通用原则

- **前后端分离**：后端提供 RESTful 接口（见 `3.API.md`），前端独立部署
- **分层**：接口层 / 服务层 / 数据层 职责分离；业务逻辑收敛在服务层
- **无状态服务**：服务端不保存会话状态，依赖 Token 鉴权，便于水平扩展
- **统一鉴权与权限**：集中式鉴权；按端 + 角色 + 数据范围控制访问（RBAC）
- **端路由隔离**：各端有专属路由前缀（如 `/sys/` `/ops/` `/app/` 等，具体见项目路由清单）；专属接口只服务对应端的 token，跨端消费须拆独立接口（细则与反例见 `.rules/3.API.md`「统一接口 + 统一授权引擎约定」）
- **多租户数据隔离**：业务数据按租户 / 实例隔离，查询强制带隔离条件，禁止跨租户越权
- **时区统一**：接口与数据层用 UTC，展示层按客户端时区转换（见 `3.TIMEZONE.md`）
- **国际化**：文案与本地化由请求上下文驱动，不硬编码（见 `3.I18N.md`）


## 分布式执行器调度（chaosplus 核心）

- **per-node 调度**：工作流中每个节点独立选 machine，不同节点可跑在不同 machine 上，同一 run 跨多机协作
- **MachinePicker**：按节点 `agent.executor` 类型匹配 machine 注册时上报的 `runtimes` 列表，取首个命中；无命中回退到 default runnerID
- **machine 注册**：daemon 连接时上报 `runtimes`（逗号分隔的 executor 列表），控制面 `Hub.MachineRuntimes(id)` 查询
- **执行器分类**：
  - SDK/CLI 类：claude（Claude Agent SDK）、codex（Codex SDK）、后续 gemini 等——需二进制检测
  - LLM API 类：mastra（纯 API，零二进制依赖）——始终可用
  - 自动化类：script（shell/python/node/bun，shebang 检测解释器）、http（REST/GraphQL，prompt 为 JSON 配置）
- **入参校验**：执行前校验 `InputSpec.Consumes` 中 required artifacts 存在于 scope，缺失即 fail-fast，不浪费 agent 调用
- **出参校验**：`OutputSpec.Produces` required artifacts 必须存在 + 非空 + 类型匹配（JSON 类须合法 JSON），不通过即 node 失败
- **验收链**：`outputValidator: "cmd:<template>"` 在工作区运行命令做最终验收，非零退出 = 校验不通过

## 云端持久化（硬约束）

- **禁止前端 localStorage 作为数据主存储**：工作流定义、运行记录、用户数据全部服务端持久化
- localStorage 仅限：语言偏好、主题偏好、通知开关等**纯 UI 偏好**——不存业务数据
- 工作流定义 → `workflows` 表（id + version 复合主键，支持多版本）
- 运行记录 → `workflow_runs` 表 + `events` 事件日志表
- **重启可恢复**：控制面启动时 `LoadFromStore()` 回灌非终态 run，UI 可见历史状态
- **事件不可变**：`events` 表 append-only，`idempotency_key` 唯一约束防重复

## 逻辑必须闭环

- 每个业务流程必须有完整的开始与结束，不留悬空状态
- 状态流转条件明确，无逻辑跳跃；非法流转必须拦截
- 异常分支（失败、超时、取消、回滚）必须有定义的归属
- 跨端联动的流程，各端状态最终一致
